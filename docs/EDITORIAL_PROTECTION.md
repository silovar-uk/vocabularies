# Editorial Draft Protection

Editorial Intakeでは、編集途中の情報を一つの保存方式だけに依存させない。

## 守る事故

### 1. 入力途中でページを閉じる

フォーム入力は約450msの間隔で自動保存する。

- 新規候補の下書きは `__new__` として保存
- 既存候補の編集途中は候補IDごとに別保存
- 再訪時、保存済み候補より新しい下書きだけを復元

候補Aを編集中に候補Bへ移っても、Aの下書きでBを上書きしない。

### 2. 更新・取り込みでキュー全体を壊す

編集キューを書き換える直前に、その時点のキューを世代バックアップへ保存する。

- 最大12世代
- 同一内容は連続保存しない
- 過去の世代を復元するとき、現在の状態も先にバックアップされる

したがって、復元操作自体も取り消し可能な方向にする。

### 3. 候補を誤って削除する

削除された候補は即時に完全消去せず、ごみ箱へ退避する。

- 最大50件
- 候補単位で復元可能
- 同じ候補IDがすでに存在する場合は、上書き前に確認する

## UI

編集キューの操作部直下に、折りたたまれた **稿保護** を置く。

閉じた状態では、

`下書きN件 · 履歴N世代`

だけを表示する。

展開すると、

- 世代バックアップ
- 削除済み

を確認・復元できる。

保護機能を常時主張させず、事故時にだけ使う設計とする。

## 保存範囲

この保護はブラウザの `localStorage` を利用するため、次には強い。

- 誤操作
- ページ再読み込み
- タブを閉じる
- 編集途中で別候補へ移る
- キューの誤更新
- 誤削除

一方、次までは保護しない。

- 端末故障・紛失
- ブラウザデータの削除
- 別ブラウザ・別端末への自動同期
- private/incognito環境での保存消失

そのため **JSONで出力** は、稿保護とは別レイヤーの外部バックアップとして維持する。

## 実行順

`editorial-protection.js` を `editorial.js` より先に読み込む。

これにより、Editorial Intake本体がキューを書き換える前に保護レイヤーが現在状態を捕捉できる。

## Storage keys

- queue: `vocabularies.editorial-intake.v1`
- drafts: `vocabularies.editorial-drafts.v1`
- backups: `vocabularies.editorial-backups.v1`
- trash: `vocabularies.editorial-trash.v1`

## 原則

稿保護の目的は「確認ダイアログを増やすこと」ではない。

**保存を自動化し、破壊的な操作を可逆にすること**を優先する。
